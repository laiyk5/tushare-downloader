## BL-001 · 配置与忽略规则的可读性 {#bl-001}

- 分类：开发流程
- 状态：已完成
- 完成版本：v0.2.0
- 关联设计／证据：[v0.2.0 发布记录](../releases/v0.2/v0.2.0/release-v0.2.0.md)

- [x] 按用途组织 .gitignore、.env.example 和本地 .env。
  - 类型：开发体验与可维护性改进（Developer Experience / Maintainability）。
  - 状态：已随 v0.2.0 实施并验收。
  - 问题：当前条目集中平铺，难以看出用途、必填项及配置之间的关系。
  - .gitignore 建议分组：Python 与构建产物、虚拟环境、工具缓存、测试覆盖率、凭据与本地配置、日志与报告、文档产物、benchmark 结果。
  - .env.example / .env 建议分组：Tushare 凭据、PostgreSQL 连接、请求与重试策略、增量/刷新策略、日志与报告、终端展示。
  - 每组添加简短注释；关键项注明用途、单位、默认值、允许值和是否必填，避免让用户从代码猜配置含义。
  - “结构化”优先采用注释分节及稳定排序，保持 dotenv 语法；是否进一步分文件或采用其他格式，留待实际需要再决定。
  - 本地 .env 含真实凭据：更新时保留用户现值，只补充缺项或整理注释；不得复制到文档、Git 或终端输出。
  - 明确测试配置与正式配置的边界，避免让用户误以为测试连接可以回落正式库。

### 验收条件

1. 用户能快速定位连接参数、下载策略和展示偏好，并区分必填项与可选默认值。
2. .env.example 与配置加载器的键名、默认值和单位一致；本地 .env 沿用相同分组。
3. 整理前后实际配置值、配置优先级及 .gitignore 匹配行为不变，尤其保留 .env.example 的例外规则。
4. 现有凭据不丢失、不泄露；文档示例只包含占位值。

## BL-005 · 常规无交易日请求过滤 {#bl-005}

- 分类：数据集扩展
- 状态：已完成
- 完成版本：v0.2.0
- 关联设计／证据：[v0.2.0 发布记录](../releases/v0.2/v0.2.0/release-v0.2.0.md)

- [x] 设计基于交易日历的请求过滤机制，减少周末、节假日等常规无交易日的无效请求。
  - 状态：已随 v0.2.0 实施并验收。
  - 按 API 的数据语义和所属市场决定是否适用；不将所有时间型接口都视为仅交易日产生数据，也不只按星期几硬编码跳过。
  - 明确交易日历来源、缓存与更新策略，以及与固定块规划、fetch/refresh/update 的关系。
  - 默认 basic 周末优化；calendar 所需日历不可用时明确失败，不自动切换规则或关闭过滤。
  - 提供 --ignore-calendar 主动绕过全部交易日过滤，保留原命令的本地记录判断；披露规则与来源假设。
  - 在计划与报告中区分“无交易日过滤”“本地有效记录跳过”和“请求成功但为空”，不把未请求日期记作远端请求成功。

### 验收条件

1. 适用接口的周末和节假日请求能被合理过滤，跨市场或不适用接口不会被误跳过。
2. 覆盖连续休市、节前节后、跨年、日历缺失/过期/修正和显式绕过的测试场景。
3. 过滤后的块规划、覆盖说明和统计口径一致，不将过滤结果当作业务完整性证明。
4. benchmark 比较实际请求次数与耗时，验证节省请求的效果及日历查询本身的成本。

- 分类：数据存储与兼容性
- 状态：已完成
- 目标版本：v0.4.0（revision 2 定稿）
- 关联设计／证据：[用户数据访问设计](../../design/data-access.md)及其 [schema 子章节](../../design/schema-contract.md)，测试条件 DA01–DA08、SC01–SC08；已定稿并实施；自动化证据已归档，最终本地验收已完成

- [x] 设计用户读取数据的标准方式，schema 契约作为其中一部分。
  - 定义只读账号的有效权限、既有用户补权、未来新增表权限，以及标准 SQL 入口。
  - 明确 stale 读取、一致性及数据内容修正边界；评估普通视图与物化视图，本版提供用户维护的可选普通视图示例，不自动创建产品视图。
  - 为下载落库的数据提供稳定、可查询并可追溯的版本化 schema 契约。
  - 明确字段名、类型、可空性、唯一键、原始字段与下载器附加字段，以及供下游使用的稳定边界。
  - 优先保持已有表结构稳定；说明 API 新增、兼容字段扩展和破坏性变更各自如何分类与处理。
  - 定义 schema 版本粒度，以及它与软件版本、设计版本和现有 schema_version/spec_version 的关系，避免重复引入含义相近的版本机制。
  - 用户应能查询当前库/数据集的 schema 版本，得知版本间结构变化，并找到对应迁移说明；具体查询和变更通知入口待设计。
  - 与升级指南和 Inspect 协调，考虑下游 SQL、Excel、研究脚本等已有依赖。

### 验收条件

1. 每个支持的数据集有与实际数据库一致的结构契约和版本标识。
2. 表结构变化可追溯至变更记录、兼容性说明和升级路径；不会静默改变契约。
3. 新旧 schema 的识别、兼容性校验及需要迁移时的行为有测试，版本策略不等同于每次软件发布都升级所有表。
4. 只读账号可按标准 SQL 读取且实际写操作被拒绝；可选视图、升级补权和读取一致性有独立数据库证据，不能只交付字段表。
