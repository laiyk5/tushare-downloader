## BL-014 · 本地检查与设计实现迭代流程 {#bl-014}

- 分类：开发流程
- 状态：进行中
- 目标版本：v0.4.0
- 关联设计／证据：[工作流草案](../../design/workflow.md)；当前版本及定稿状态见关联设计入口；目标软件 v0.4.0

- [ ] 评估减少 GitHub PR 和远端服务在版本提交链条中的依赖，并降低不必要的发布频率。
  - 尽量在本地完成代码、数据库、文档构建和设计一致性检查，明确可复用的证据、远端独有验证和正式发布门槛。
  - 原提案曾考虑草案期间实现；维护者已明确修正：只有非草案设计可实施，测试条件先行，设计变更重新定稿后继续受影响实现。软件正式发版由人类提出；本地足够完成的工作不触发 GitHub workflow。
  - 区分本地提交、草稿修订、PR 集成、设计定稿和软件发布，不要求每次文档或证据小更新都单独发布。
  - 明确最终设计、实现提交、验收证据的对应关系，以及定稿后的变更规则；不通过事后降低验收标准来迁就实现。
  - 明确保留哪些 CI、分支保护和 Pages 部署检查，以及适合合并提交的时机；本条是流程评估，不授权立即关闭现有保护或修改定稿历史。

### 验收条件

1. 有清晰的本地到发布流程，说明各阶段输入、检查、产物及失败处理。
2. 相同代码的重复检查有合理复用规则，确需 GitHub 的操作集中进行，仍能追溯最终候选的验证结果。
3. 用一个后续版本实际验证流程，记录 PR/发布次数和必要等待，评估减少依赖的效果。

## BL-011 · 升级方法与用户指南 {#bl-011}

- 分类：文档与升级
- 状态：进行中
- 目标版本：v0.4.0
- 关联设计／证据：[升级指南草案](../../design/upgrading.md)，测试条件 UP01–UP09；待定稿与实施

- [ ] 从 v0.4.0 起，将已有用户升级路径纳入产品设计和文档。
  - 覆盖上一个 major 和上一个 minor 版本的用户；设计时明确具体来源版本、支持矩阵、直接升级或分步升级路线。尚不存在的上一 major 明确标为不适用。
  - 区分首次安装、原地新增 API 表、已有表结构迁移、配置变化及权限变化，说明数据、下载记录和下游依赖如何保留。
  - 首条指南为 v0.3.0 → v0.4.0：本轮沿用六表和连接配置，无需数据库迁移，init-db 仅作可选校验；不追补已封版的 v0.2.0 → v0.3.0 指南。
  - 规定升级前准备、命令、预期结果、升级后验证，以及失败恢复和降级限制；示例默认 Bash，SQL 片段明确标注。
  - 后续设计需要明确兼容性影响；有升级影响时同时更新指南及测试，不能仅给新用户初始化步骤。

### 验收条件

1. 用户能按来源版本找到可执行的升级路径；不支持的跨版本跳跃和必要中间版本明确可见。
2. 从受支持旧库夹具升级后，数据、数据库身份和下载记录按兼容契约保留；重复执行及失败回滚行为可验证。
3. 新增独立 API 支持不要求删库；已有 schema 变更必须有明确迁移路径和适用边界。

## BL-010 · 按命令组织日志目录 {#bl-010}

- 分类：CLI 与可观测性
- 状态：进行中
- 目标版本：v0.4.0
- 关联设计／证据：[日志目录草案](../../design/log-layout.md)，测试条件 LG01–LG09；待定稿与实施

- [ ] 在配置的日志根目录下，按命令分子目录存放日志。
  - 例如 `logs/fetch/`、`logs/refresh/`、`logs/update/`；实际根目录沿用配置，目录名按规范命令名统一，缩写不产生另一套目录。
  - 明确其他会产生日志的命令归属，以及执行标识、轮转分片、启动时路径提示和报告链接的组织方式。
  - 明确旧日志保留和兼容读取策略，不因调整目录而隐式删除或迁移用户文件。
  - 与跨日志分片连续监看事项协调，但不要求同时实现监看入口。

### 验收条件

1. 不同命令写入各自子目录；同一命令的全名与缩写采用相同路径规则。
2. Rich/plain、quiet/verbose 下日志路径和报告链接均准确，轮转分片完整保留。
3. 自定义根目录、并行调用的文件名隔离、目录创建失败和旧日志保留有明确行为与测试。

## BL-017 · development 版本产物目录整理 {#bl-017}

- 分类：文档与升级
- 状态：进行中
- 目标版本：v0.4.0
- 关联设计／证据：[版本产物目录草案](../../design/development-layout.md)，测试条件 DL01–DL09；维护者已明确纳入本轮，待定稿后实施

- [ ] 重新组织 docs/development 下的文件，按版本归集产物，避免验收记录、基准、终端截图和其他证据在目录中平铺。
  - 同一版本的相关产物集中存放；相同 major.minor.x 的文件归入同一个 major.minor 系列目录，不为每个 patch 在 development 根目录创建平级目录。
  - 例如 v0.3.0、v0.3.1 的产物共同归入 v0.3 系列；系列内部如何区分 patch、产物类型及共享证据，留待设计，不因聚合而混淆实际来源版本。
  - 区分长期维护的开发指南、backlog 等公共文档与版本专属产物；明确命名、索引、导航及后续新增文件的落点。
  - 迁移现有产物并同步相对链接、Zensical 导航和必要的脚本引用；已分享的网页地址评估重定向或兼容入口。
  - 保留历史证据内容、原始字节、软件/设计 SHA 和版本归属；不改写已发布标签，不把旧证据包装为新版本验证。

### 验收条件

1. development 根目录不再随每次 patch 发布持续增加平级版本目录；同一 major.minor 系列可集中查阅。
2. 同一版本的产物有明确归集入口，能准确定位每个 patch 的记录与证据，不发生覆盖或版本混淆。
3. 迁移前后产物完整、历史证据不变，站内链接、导航和相关脚本有效；旧公开链接有明确兼容处理。
4. 文档说明后续新增产物的放置规则，本地严格构建与目录/引用核对通过。
