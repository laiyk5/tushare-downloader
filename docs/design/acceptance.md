# 当前设计验收标准

**交付目标：v0.4.0；设计 revision 4（定稿）；业务基线为 v0.3.0。**
本文规定如何验收，不记录软件已经通过。当前没有在本文执行或勾选任何软件验收项目。
设计入口和修订历史见 [index](index.md)；新执行证据应另存 development，明确最终软件和设计 SHA，不覆盖既有发布验收记录。

## 1. 范围、判定和证据

本文是当前设计的验收门槛清单；各章节仍负责行为规范和测试用例细节。冲突必须先澄清正文，不能通过改测试或降低标准掩盖。
覆盖既有 daily_basic、stock_basic 和新增 daily、adj_factor、stk_limit、suspend_d，以及 fetch/refresh/update、list、init-db、clean。抽象类型的未来扩展、未注册 API 不属于本版实现门槛。
每个编号均为必需项，除明确标注的发布项或待决项。不通过、不执行、被跳过、预期失败都不能算通过。

| 验收阶段 | 通过条件 |
| --- | --- |
| 设计可实施 | 规范引用一致，测试预期可判定；实现相关歧义已澄清，发布待决事项明确登记 |
| 实现验收 | A–J 及 L–O 全部完成并有证据；未支持功能不能以旧版已验收代替 |
| 发布验收 | 实现验收通过，K 全部完成；已选 MIT 的声明和第三方分发义务落实 |

证据至少记录：验收编号、软件完整 commit SHA、采用的设计 commit SHA/版本、执行环境和依赖版本、命令/测试位置、预期与实际、退出码、脱敏产物路径或 CI 链接、结论。
同一测试或执行可以覆盖多个编号，不要求每个编号新建脚本。沿用既有有意义测试，不机械重复实现。
六种终端模式比较同一初始数据库和输入下的结果语义；忽略运行 ID、路径、时间戳、耗时等合理差异，不要求报告字节相同。
旧版证据只可复用于未改变且有明确变更影响分析的环境/部署事实；候选软件仍需运行完整回归。变更后的能力必须有当前实现证据。

## 2. 检查中确认的边界与未决项

1. 只增型快照、可变型时间范围等尚无注册 API；无需为了满足“类型笛卡尔积”添加产品功能。现有纯算法的边界测试仍保留。
2. 程序自有提示/报告使用英文；API 原始错误或数据可以是中文，但须有英文上下文且安全转义。
3. 日历模式失败不能自动切换 basic/off；basic 默认不需要外部日历。日历内容真实与永久正确不是可证明的验收目标。
4. 不把“日历获取成功”误记为数据下载成功，不把“快照子请求成功”误记为已提交。
5. `report.md` 是计划与最终结果记录，不是实时进度文件；强制终止可留下未完成报告，不能保证必然产生最终摘要。
6. MIT 已由维护者选定；根 LICENSE、元数据和 README 必须一致。第三方材料保留其许可，数据授权不由代码许可授予。选择完成不等于最终分发检查完成。
7. 跨日志分片连续监看便利入口移入后续 backlog，不属于 v0.3.0 范围。当前最低承诺是分片完整保留、最终报告列出全部实际分片、明确单文件 tail 的限制；不得宣称已实现自动跟随。增加该能力需先明确规范再验收。
8. 当前 HTML demo 是较早的模拟布局。它可以辅助评审，但不能替代真实 Rich 终端验证；若保留旧版，必须醒目标注差异，不能伪称与当前实现完全一致。

2. **不得自主扩大**：不新增终端/OS/数据库版本、API、账号组合、尺寸、压力档位、随机种子或跨维度全排列；不为追求测试数/覆盖率/“再保险”增加验收要求；不把发布 CI、Pages 部署提前变成本地完成门槛。
3. **允许补验证的具体触发**：实际失败或用户报告；当前改动触及某条已定稿契约但无有效证据；证明原证据不适用的代码/依赖/环境差异；测试不确定性需要定位。记录“现象或差异 → 需求编号 → 最小验证 → 停止条件”，只扩大到解释该问题所需的范围。
4. **新风险假设不是自动授权**：若只是潜在改进，加入 backlog。若发现会影响本版正确性的设计缺口，报告具体反例及影响，先修设计并由维护者确认，再扩大验收；不能隐瞒已知缺陷，也不能无限追查假设。
5. **重跑边界**：通过且相关输入未变化的检查立即关闭。新增实现修复后重跑失败项和受影响范围；如果最终候选的软件树变化使完整回归证据不再适用，则在修复稳定后集中补跑一次。纯记录、颜色 Demo 或无关文档修改不触发软件全量回归。
6. **停止**：所有固定需求都有合格的新证据或可复用证据、无未解决实际缺陷，即停止技术验证。只剩必要用户决策或代理无法访问的具体外部条件时明确列出阻塞，不新增测试、额外审计轮次或背景任务来填充等待。未执行的终端验证／发布项不标通过；可选主观体验不作为默认阻塞；按工作流区分软件验收与发布。
7. **目标模式不增加权限或范围**：“继续追踪目标”仅推进上述清单。再次完成性核对只核对缺项与发生变化的证据，不重新发明门槛；同一已关闭项不因自动续轮重新打开。

### Q.3 执行预算与关闭条件

先写测试并确认缺目标行为导致失败，再实现。顺序为规划/授权快速测试 → 受影响数据库和 CLI → 稳定候选一次必要完整自动回归、构建/安装、文档检查。MG06 一条旧库真实公开链，MG07 一条 PTY，MG08 一次体验库建立/重置；其他故障用规定夹具，不以不同名字重复端到端操作。

网络预算为零 Tushare 请求；本轮无生产访问、无远端 workflow/发布。不添加平台/尺寸/账号全排列，不重跑已关闭且未受改动影响的检查。失败后只重跑失败项与相关影响集；按 O.4 的明确触发处理额外验证，设计缺口先修设计，不在实现中扩大门槛。
