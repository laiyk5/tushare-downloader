# 交易日历过滤设计

**设计版本：v0.2.0-draft.1**

## 原则与适用性

日历是请求优化依据，不是完整性证明。保留原固定地址块算法，本版仅对明确按交易日产生数据的单日块启用过滤。
快照接口 `stock_basic` 不适用；不按周末硬编码，不改 block_id，不把休市日期写成成功下载。

来源采用 [Tushare trade_cal 官方文档](https://tushare.pro/document/2?doc_id=26)（2026-09-14 核对）。
它提供按交易所和日期范围查询的开闭市标记。当前文档列举 SSE、SZSE，但没有明确 BSE 的支持约定。
因此不能据此断言 SSE 日历代表 daily_basic 的全部市场。

每个适用 ApiSpec 使用一份明确的市场映射。只有全部目标市场已验证，才启用过滤。
daily_basic 的 SSE/SZSE/BSE 覆盖是本版待验证门槛：实施时验证接口与实际日历响应，保存不含凭据的证据。
没有证据时，该 API 不过滤；不得偷偷忽略 BSE，也不增加按股票拆请求作为补救。
该验证结论在实现评审中记录，必要时修订本草案后再启用。

## 缓存与准备阶段

缓存按交易所、自然年分文件，包含格式版本、来源、交易所、年份、取得时间和逐日日历。
请求明确指定交易所、全年起止日期，不指定 is_open 过滤；仅保存字段与日期解析成功、无重复冲突的响应。
缺失日期分类为 unknown，不需要递归补齐。缓存不保存 Token 或请求认证信息。
文件用临时文件加原子替换写入；坏文件、格式不支持、时间戳在未来、过期缓存视为不可用。
程序每次执行固定使用一份读取/刷新后的快照，中途不改变过滤结论。

先按 fetch/refresh/update 原规则排除已有有效下载块，再为剩余候选日期准备涉及的市场/年份。
一次执行每个市场/年份最多发起一轮刷新（包含客户端有限重试），共用所有 API 的限速预算。
权限不足、网络失败、解析失败或缓存 I/O 失败均记录警告，受影响日期回退原下载流程。
日历失败本身不改变下载退出码，不计入数据块连续失败阈值；数据执行和日志失败仍遵守原退出规则。
日历错误不能静默吞掉；报告给出回退原因及次数。

`--dry-run` 不请求远端、不刷新或写缓存：只用有效缓存，明确提示实际执行可能因刷新日历而调整计划。
全部候选块已本地跳过时，不请求日历。准备阶段显示活动状态，不提前展示数据 ETA。
可直接删除缓存目录使下次重新取得日历；无需新增清理命令。缓存按年月边界构造路径，不使用远端任意字符串作为路径。

## 规划与绕过

对每个剩余单日候选块：

1. 不适用或 CALENDAR_FILTER=off：按原算法请求。
2. 任一市场该日 open：请求。
3. 所有目标市场都有有效记录，且全部 closed：过滤。
4. 其他情况（包括任一 unknown）：请求。

fetch、refresh、只增型 update 使用同一过滤规则；可变快照 update 不调用日历。
为下载命令增加低频 `--ignore-calendar`，本次跳过日历读取与请求。它不改变本地新鲜度判断。
完全重新核对历史数据使用 `refresh --max-age 0 --ignore-calendar`；只设置 max-age 0 仍遵守日历偏好。
报告中保留日历来源、快照取得时间和筛除日期；下一次重新规划允许日历修正后重新请求。
过滤不删除本地行、不标记 stale，也不产生 meta.slices 成功/空结果。已有异常行可以通过上述强制刷新入口核对。

## 统计

新增 G 为日历过滤块数，K 仍是原本地有效跳过数，P 是实际计划执行的数据块数。
总范围块数 T = K + G + P，各分类互斥，先判断 K 再判断 G。
P 内沿用原成功、空、失败、未尝试等分类恒等式；数据 ETA 的分母仅为 P。
calendar_requests 单独计 HTTP 尝试次数（含重试），data_requests 同理；总 HTTP 次数为两者之和。
不把日历请求混入数据成功率或行计数。性能总耗时包含日历准备、限速等待、下载和写库。
未知日历但最终正常请求的数据块不另算失败。全范围 K/G 且无执行错误可退出 0，明确显示零数据请求。
覆盖报告把“按日历过滤”与“已取得数据”“成功空响应”“失败/未尝试”分开；不声称已证明业务完整。

## 测试与 benchmark

等价类覆盖全 closed、任一 open、任一 unknown、接口不适用、显式关闭/绕过；验证 K 优先于 G。
边界覆盖假期连续段、节前后、跨年、闰日、过期边界（age <= max_age 有效）、未来时间戳、缺行、重复冲突和市场缺失。
故障覆盖权限错误、重试耗尽、损坏文件、原子写失败；确认 fallback 发出原数据请求，未增加成功请求记录或 stale。
集成测试验证候选规划、缓存第二次复用、日历修正后重新计划，以及 dry-run 无远端副作用。

benchmark 使用固定日历/数据响应及相同空库或可还原数据库：off、冷缓存 auto、热缓存 auto、日历失败 fallback 四组，至少各五轮。
记录总耗时中位数、范围块数、K/G/P、日历与数据 HTTP 尝试数、重试等待和写入计数。
确定性用例要求 auto 恰好减少 G 个数据请求，fallback/off 的数据请求集合相同；不设依赖网络的固定加速倍数。
另选月度与跨年范围实测权衡：冷缓存可能更慢，应如实报告；不能只列数据请求减少量而隐去日历成本。
