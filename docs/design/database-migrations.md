# Setup 版本迁移与数据库环境

**v0.4.0 / revision 6 定稿，维护者已授权实施。** 本章替代 revision 5 中独立 `migrate` 入口及 setup 发现迁移即退出的契约。revision 5 的真实验收、设计标签和实现记录保留，不改写成新行为已交付。数据键修正、无损约束与 Inspect 总览继续有效。

## 1. 用户入口 {#entry}

数据库连接、初始化、补齐和升级统一由 `setup` 处理。用户无需先决定操作类型，也无需选择数据集或逐个执行迁移命令。

读取配置 → 连接并读取身份/版本/结构 → 生成完整有序计划 → 收集必要凭据 → 展示差异及后果 → 明确确认 → 依次执行 → 验证并汇总。

- Ready：无写入，直接结束。
- 新库或缺独立 API 表：沿用创建/初始化/补表流程，直接建立当前结构；不先建立旧表再升级。
- 已知旧结构：显示 Migration needed，并在 setup 内列出从当前版本到目标版本的全部迁移步骤。
- 未知身份、结构漂移、比当前程序更新的数据库或不完整路径：Unsupported，零变更，不降级、不删库重建。
- 连接或读取失败：Unknown，修正连接/权限后重查，不能当作新库。

`migrate` 是未发布 v0.4.0 候选新增的入口。本修订实施时移除该顶层命令及帮助入口，不保留别名或第二套执行流程；现有用户指南、错误提示、CLI 参考改为 setup。历史证据中的旧命令不改写。下载、init-db、inspect 只报告需运行 setup，不隐式迁移。

## 2. 按版本计算迁移链 {#versions}

复用 `meta.schema_info.schema_version` 和 `specs`，前者表示内部元数据结构版本，后者表示每个 API 的存储契约版本；公开 schema 版本仍由这些版本映射得到。它们与软件发行版本不同：软件更新但数据库结构不变时，无需迁移。当前修订不新增重复的“软件数据库版本”、持久任务或迁移状态表。

迁移定义随软件包提供（开发候选在隔离库验证，正式包用于生产），使用一个小型、显式有序注册表。每一步固定：稳定 ID、作用域、来源/目标版本、结构及权限前置条件、依赖、变更说明、执行函数和结果校验。迁移函数只执行审查过的 SQL，不根据 schema diff 自动生成修复，不导入外部插件。

规划器读取实际版本向量，选出通往程序期望版本的连续步骤；跨多版按顺序执行，不能只运行“上一软件版本到当前版本”的脚本。步骤按注册表显式顺序排列，注册校验要求依赖出现在使用者之前；依赖反序属于无效注册，拒绝而非运行时自动拓扑调度。同一作用域的下一步来源必须等于前一步目标，不按版本字符串字典序排序。跨作用域可有多个独立步骤，按注册顺序执行，不把这种情况当作歧义；同一作用域/来源有两个竞争的后继才是歧义。稳定 ID 只用于日志及引用，不另做版本事实来源。注册表缺环节、环路、同一状态存在歧义路径均拒绝；无关数据集不迁移。已发布步骤的 ID 和语义保持稳定，后续追加步骤，结构变更登记与实际 DDL 必须一起提交；仅改变请求语义的 spec 升级也需显式无 DDL 版本步骤，不能直接改映射绕过覆盖失效规则。不能用“每次只保留最新迁移”破坏跨版本升级。

当前唯一真实结构迁移 ID 为 `suspend_d-spec-1-to-2`，作用域为 API suspend_d；迁移为 `suspend_d` spec 1 → 2（公开 schema 1.0.0 → 2.0.0）；内部 schema_version 仍为 1。已经执行 revision 5 迁移的库直接识别为已完成，不重复 DDL。其他缺表按当前契约创建，不伪造迁移历史。多个连续版本的执行器测试使用明确标识的合成夹具，不冒充产品已有三代真实结构。

版本向量允许只初始化部分 API：未登记且表不存在是缺项，直接创建目标结构；已登记但表缺失、未登记却同名表存在都属于漂移，不能借补表抹掉数据损坏迹象。不得因未初始化无关 API 而补跑它的旧迁移。内部 schema 的升级必须在注册表中声明所需 API 版本与解码规则；本版只支持内部版本 1，不虚构其他内部版本迁移。

有限支持边界：v0.3.0 正式基线和已知 v0.4.0 候选结构均有明确识别路径；未来支持范围按升级指南扩展。承诺已声明支持范围内的跨版本迁移，不承诺猜测任意手改库或无限久远未知版本。

## 3. 计划、执行与失败恢复 {#execution}

启动检查仍只读目录/身份/版本，Ready 路径不扫描业务行。只有已识别迁移路径时进入独立的只读迁移预检阶段，允许该步骤必要的数据有效性检查；suspend_d 检查空类型与依赖，预览行数允许显示未统计，不为展示额外 COUNT 全表。没有 Token 也可完整运行 setup。

计划必须先完成全链版本/依赖解析及当前可判断的身份、权限、数据/对象阻塞检查，展示真实目标 host/port/database、database_id、各步当前→目标版本、涉及数据集、锁/依赖风险、备份要求及覆盖记录影响。后续步骤依赖前一步产生的对象，其动态前置条件在该步事务中重查，不能承诺能提前发现所有运行错误。

迁移链在同一有界工作进程、同一执行连接内持有已有的会话级 writer advisory lock，覆盖全链至最终结构复核；每步提交不释放该锁。进程退出/连接关闭释放锁，不在不同步骤的工作进程之间传递连接或锁。外部不遵守此锁的 DDL 仍由每步实际结构复核和对象锁防护。执行前取得 writer advisory lock，锁内重查身份与版本；确认后的事实变化则停止并重规划，不能悄悄扩大确认范围。setup 原有创建/补表/补权动作继续使用共用计划，不建立第二套执行器。全链已知阻塞不得先做授权或补表再报告；需要迁移时先迁移现有结构，再按依赖补表/补权，最后验证访问。

每一步一个原子事务：锁定涉及对象 → 重查 → 执行 → 校验 → 同事务更新对应版本 → 提交。数据库版本不能领先或落后于本步结构。保留 database_id、已有数据、授权和用户对象；禁止 CASCADE、自动删库、猜测清洗。期限统一如下：启动目录检查沿用 CONNECT_TIMEOUT_SECONDS + INSPECT_TIMEOUT；独立迁移预检按每个待执行步骤使用 SETUP_STEP_TIMEOUT（默认 60 秒、最大 10 分钟），包含连接、只读 SQL 和结束事务；每个写步骤也使用该预算，包含连接、SQL、校验及提交。每条语句上限为 min(60 秒, 本步骤剩余预算)，锁等待上限为 min(5 秒, 本步骤剩余预算)，不能按 SQL 重置步骤时钟。后续未知结构的纯定义检查不连接数据库；已经能运行的预检 SQL 各执行一次。客户端监督链内逐步期限，超时终止当前工作并停止后续步骤；持锁跨步不取消这些期限。

整个迁移链不是一个大事务。第 1 步成功、第 2 步失败时，保留第 1 步，回滚第 2 步，后续不执行。日志和摘要明确 Completed / Failed / Not attempted 及实际版本。重跑 setup 重新读取事实，跳过已提交步骤；无需 resume 或任务管理。

提交确认丢失标记 Unknown，不自动重放。下一次只读检查以真实版本与结构判定结果；若无法判定则停止。中断、连接/日志错误和权限不足保留已提交事实。日志起始失败时零变更；中途失败停止后续动作，不能把已提交步骤报为回滚。迁移前备份由用户按升级指南完成；计划明确提示备份，但不新增备份文件检测或重复确认开关。setup 不自动备份、恢复或承诺数据库之外的依赖可回滚。

## 4. 交互、headless 与日志 {#interface}

交互沿用顺序问答、编号编辑和 Rich/plain 输出。计划中说明升级改变的唯一键/读取契约及备份后果；执行结构迁移前要求输入真实目标数据库名确认。这次确认覆盖展示过的整个有序计划，不逐步重复确认；修改连接或计划后重新确认。不以空回车或默认 yes 授权。

headless 默认只读：需迁移返回 4，Ready 返回 0。`setup --headless --apply` 对普通初始化/补齐沿用原规则；计划包含结构迁移时，另外要求 `--confirm-database NAME` 与实际连接数据库名精确匹配。该选项仅与 headless --apply 配对，组合错误或名字不匹配返回 2；缺确认返回 4，零变更。凭据仍通过既有私密文件或安全认证来源提供，不新增密码参数。交互不接受该开关来跳过现场确认。

```bash
# 拟实现行为：默认检查并交互引导迁移
tushare-downloader setup
# 自动化先检查，再显式授权完整计划
tushare-downloader setup --headless
tushare-downloader setup --headless --apply --confirm-database tushare_dev
```

若计划不含迁移，headless --apply 可带匹配的 --confirm-database（便于脚本幂等重跑），仍核对真实目标名；不匹配退出 2。合法配置下，状态优先级为 Unknown → Unsupported → Migration needed → Needs configuration → Ready；同时列出次级缺项，不把 reader 缺项掩盖。已证实的数据空类型、依赖阻塞、非预期所有者是 Unsupported（写前退出 5）；因权限/连接/超时无法判定则 Unknown（退出 1）。已识别迁移而仅缺执行所需的临时凭据时，保持 Migration needed 并附 Needs configuration，headless apply 返回 4；连接检查实际失败仍是 Unknown/1。不得把未成功验证的密码当成已齐备认证。

权限依旧最小化：迁移执行账号须拥有涉及表和元数据，不因为有管理员连接就暗中提权或改变所有权；缺必要凭据先补充、重查。读账号无需因纯约束迁移被强制索要密码；确实改变 reader 访问授权时按原 setup 验证规则执行。

退出码沿用 setup：0 成功/Ready/交互正常未写取消，1 运行失败或结果未知（含部分提交），2 参数错误，3 writer 忙，4 已知需配置或迁移但未授权/缺输入，5 不支持且尚未写入，130 中断。开始写计划后的执行失败不得用 4/5 掩盖部分提交。

所有新操作日志写入 `LOG_DIR/setup/`（默认 logs/setup/），开头输出路径；步骤事件包含稳定 migration ID、scope、from/to、outcome、耗时及 database_id，禁止凭据。保留现有 event_version=1，仅增加可选迁移字段；旧 `logs/migrate/` 记录无需移动。人类摘要先显示当前状态、迁移链和最终版本；机器读取日志，不新增 stdout JSON 模式。

## 5. 开发与生产数据库约定 {#environments}

这属于开发纪律，不在产品代码内按库名拦截，也不强制用户采用这些名称。

| 用途 | 名称/配置 | 访问代码 | 重置约定 |
| --- | --- | --- | --- |
| 开发体验与验收 | 固定 `tushare_dev`；项目私有 `.env.dev` | 工作分支和候选构建 | 可重置，重置前核实目标并记录；不用于保存不可替代数据 |
| 自动测试 | 现有隔离测试服务的唯一临时库；沿用 TEST_DATABASE_URL | 测试夹具 | 按测试生命周期创建清理，不借用体验库 |
| 生产使用 | 现有实际使用库及 `.env`，不重命名 | 仅正式发布标签对应的未修改代码/发行包 | 禁止为开发、调试或验收重置/写入 |

本项目开发体验库计划放在现有隔离测试 PostgreSQL 服务（计划端口 55433；实施时系统拒绝绑定，已在同一隔离数据目录改用 55434，配置/记录以实际端点为准），与日常生产服务隔离；WSL 可达 host 和账号从已验证的开发连接填写，不能把 localhost 或现有生产凭据直接当作正确配置。revision 6 实施记录单独记录开发库建立与重置结果。开发库是长期复用的体验目标，自动测试仍单独建库。

每次体验使用显式 `-c .env.dev`；由于 PG* 环境优先于文件，执行前检查生效的 host/port/database/current_user/database_id，先消除生产环境变量覆盖。不仅凭文件名或命令参数判断隔离。凭据文件不提交 Git；模板只用占位符。

重置开发库不是 setup 功能：开发者先精确确认目标属于隔离服务且库名为 tushare_dev，确认无人使用和没有需要保留的验收证据，再重建该库，禁止通配清理、集群级角色清理或误删其他库。验收可重现步骤需先记录，不能重置后声称旧库升级已验证。开发用角色不得与生产共用集群级账号；现有共享测试服务不因重置体验库而停止或清空。

生产库只供正式代码访问，包括 inspect/setup/只读调试；候选代码即使只读也在开发库验证。正式发布由人类提出，验收通过、本地 commit 或定稿不等于正式代码。生产升级由正式版本的 setup 在用户授权后执行；无自动生产迁移。需要生产样本时由正式工具导出经许可的数据到隔离库，再供候选验证。
