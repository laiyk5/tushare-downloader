# 升级支持与用户指南设计

> revision 5 合并修订：本章原有“无迁移／直接兼容”结论只适用于 revision 2–4 原范围。suspend_d 的版本识别、显式迁移、退出码和升级路径以 [API 修正设计](api-contract-validation.md)为准；未知结构不得猜测转换。该补充已统一定稿，实施状态见开发记录。

归属 [当前设计](index.md)，对应 [BL-011](../development/backlog/index.md#bl-011)。本项交付升级政策、英文用户指南和可重复验证的升级路径；不引入通用 migration 框架，不替 BL-013 决定 schema 版本化方案。

## 1. 支持范围

从软件 v0.4.0 起，每个发布版本应说明旧用户的升级路径。指南区分软件升级与数据库迁移，不能要求仅因增加独立 API 表就重建数据库。

| 来源 | 发布时的要求 |
| --- | --- |
| 同 minor 的旧 patch | 说明兼容性；若需操作必须列出，不能仅凭版本号假设无影响 |
| 上一个已发布 minor | 列明来源版本、目标版本及直接或分步路线；至少以该 minor 最新发布 patch 做真实旧版本升级演练 |
| 上一个已发布 major | 给出其最后维护 minor 的最新 patch 起步路线，必要时通过中间版本升级；在 0.x 尚无上一 major 时明确不适用 |
| 更早版本、非标准或手工修改的库 | 明确列出已验证路线，或要求先到指定中间版本；不能未经验证宣称任意跨版直升 |

上一 minor 按发布历史选取：跨 major 首版优先覆盖上一 major 的最后维护 minor，不虚构不存在的 minor。若同一来源系列中存在结构或配置差异，需追加代表性验证或收窄并明确来源范围，不能用最新 patch 的结果替所有差异签核。必须区分“提供分步路线”和“保证所有版本可直接升级”。

首条要求是 v0.3.0 → v0.4.0；v0.3.0 已封版，本项不再补写或重新演练 v0.2.0 → v0.3.0 升级指南。旧验收事实与历史证据保留。v0.4.0 是目标软件版本，尚未实现或发布；发布前将实际候选 SHA 纳入验证记录。对 v0.2.x 等更早用户明确本轮指南以已有 v0.3.0 环境为起点，不宣称其可直接升级，也不为满足本项追补旧版教程。

## 2. 当前已知升级契约

本轮四项 working 不新增 API、不修改已有数据库字段、唯一键、meta schema 或 API spec 版本。v0.3.0 → v0.4.0 应直接沿用六张 raw 表和现有元数据，无需增表、迁移数据或重建库。

六表的数据（含 stale）、meta.slices 下载观察记录和 database_id 保留。init-db 可作为可选的结构校验步骤，不是本次软件升级必须执行的迁移。对已登记且兼容的表重复初始化不改变其内容；遇到不兼容结构则明确失败，原事务回滚。只有将来新增独立 API 时才通过 init-db 增表；已有结构变化须先有对应迁移设计。

用户仍使用 PGHOST/PGPORT/PGDATABASE/PGUSER/PGPASSWORD/PGSSLMODE 连接设置及原配置优先级；普通 DATABASE_URL 不是当前下载器支持的连接键，不能与测试专用 URL 混淆；不引入新必填键，不从 .env.example 覆盖 .env。未知键、重复键、注释与当前有效值不得由升级命令擅自重写。临时验证连接由独立环境明确提供，不能误用生产配置。

本次不新增表和角色授权，现有 writer/reader 权限应保持，无需为升级重新 GRANT。指南说明可选 init-db 沿用现有 writer 连接，并提供 reader 的只读抽查。default privileges 对未来新增表的作用作为数据库维护文档中的背景保留，不作为本次升级必须操作的步骤。

本轮日志路径调整不迁移数据库：新调用写入 LOG_DIR/<command>/，旧日志和报告保留，根目录通配脚本需调整。具体目录规范以 [日志布局](log-layout.md) 为准，只有包含该功能的实际目标版本才列为已生效变化。

## 3. 英文指南的组织和步骤

实施时新增 `docs/operations/upgrading.md`，导航名 `Upgrade`；从数据库维护、快速开始和版本记录提供入口。数据库文档明确区分首次创建角色/数据库和已有库升级。用户页使用英文，不放内部待办或试行提醒。

每条路线依次说明来源/目标、变化与不变项、准备、操作、验证、失败恢复和降级限制。所有示例默认 Bash，SQL/psql 片段明确标注；不会要求所有用户为升级安装 WSL 内 PostgreSQL 服务器。

v0.3.0 → v0.4.0 的操作顺序如下（将于实施阶段整理为英文指南）：

1. 查看当前软件版本，确认目标标签和原数据库连接方式；停止自己的下载写入进程，不要求停止 PostgreSQL 服务。检查 Git 工作区，存在本地修改时先保存，不能用 reset --hard 清除。
2. 安全保留原配置并确认既有备份策略。本次没有数据库迁移，不要求仅为更新软件重新备份全库；如要执行会改动结构的数据迁移，必须先按 [备份指南](../operations/backup-restore.md) 准备并验证恢复。本次可选结构校验不构成删库或恢复的理由。
3. 在目标版本正式发布后，更新到指定发布标签并同步锁定依赖。源码安装示例可用 `git fetch origin tag v0.4.0`、`git switch --detach v0.4.0`、`uv sync --locked`。源码目录变化时明确 .env 与相对日志路径仍由 cwd 决定；发布依赖获取不等于触发 GitHub workflow。
4. 沿用原数据库连接启动新软件，无需数据库迁移。可选执行 `uv run tushare-downloader init-db` 校验现有结构；不要求再次 CREATE DATABASE、运行 clean 或切换到空库。
5. 核对版本、数据库身份、六张既有表、原数据与观察记录，并以 reader 验证原查询仍可读。用 `list` 检查六个接口登记，但明确 list 不能证明数据库已初始化。最后可使用已覆盖历史范围的 fetch --dry-run 验证规划，不自动下载大量历史数据。

指南应提供只读 SQL：查询 meta.schema_info 的身份和 spec 登记、检查六张 raw 表是否存在、比较升级前后既有表行数与最新日期、抽查 meta.slices。数据量大时说明完整计数成本，使用已有基线或小范围样本；单凭数量相同不能证明数据未变化，完整内容保持由独立升级测试验证。

## 4. 失败恢复与降级

依赖同步失败先修复软件环境，不继续数据库操作。init-db 校验、权限、同名对象或事务错误时保留原库，定位问题后重试；无成功确认时先查数据库实际状态，不能盲称全部回滚或手工删除半成品。连接丢失的提交确认问题按既有 unknown 边界处理。

恢复应先在新建的独立数据库中完成并验证，再由用户决定切换连接；不能在错误处理流程自动覆盖生产库。恢复旧备份会丢失备份后的修改，指南必须明确该时间边界。

软件退回旧版本不自动降级表结构。本项不承诺任意软件降级兼容性，也不提供自动 down migration；未验证的降级路线明确不支持。仅新增表时旧软件可能仍能使用原接口，也必须单独验证后才可推荐，不以“理论上应当能用”作为用户操作指南。

## 5. 结构变化的发布约束

后续若修改已有字段类型、键、meta 或 spec 兼容规则，应先设计独立迁移步骤、失败边界和数据保留策略，再实施并验证；禁止把不兼容变化塞进 init-db 静默处理。升级文档必须说明下游 SQL/Excel/研究脚本的影响。BL-013 已进入 working，其 [用户数据访问草案](data-access.md) 包含稳定 schema、reader 补权与可选视图；仍须定稿才实施。

定稿设计与发布记录分别说明数据库是否无需改动、仅需 init-db 增表，还是需要特定迁移。只有人类提出正式发布时，才执行必要发布流程；指南中给用户的升级命令不构成代理现在执行生产升级的授权。

## 6. 先于实现确定的测试条件

| 编号 | 条件 | 预期与证据 |
| --- | --- | --- |
| UP01 | v0.3.0 发布标签在独立环境创建六表、写入合成 active/stale 及观察记录；切换到 v0.4.0 候选 | 不运行迁移即可使用原库；六表、身份、spec、全部样本及观察记录在首次下载前不变；记录来源与候选 SHA |
| UP02 | 对成功升级后的库再次初始化 | 身份、数据、记录不变，无重复对象；SQL 对照 |
| UP03 | 库身份或已有字段结构不兼容，可选 init-db 校验失败 | 非零失败，不接管或修复外部结构，六表数据与元数据不被部分更新；故障夹具 |
| UP04 | 自定义连接、环境优先级、dotenv 重复/未知键与缺少新可选项 | 配置保持原语义；文件字节不被升级步骤改写，不泄露凭据 |
| UP05 | 已有 writer/reader，升级前记录 ACL | 升级后权限不变，reader 可读原六表且不能写，不要求新增 GRANT；独立权限测试 |
| UP06 | 备份后恢复至独立库，按指南核对身份、raw/meta 和 reader | 可复现恢复与连接切换准备，不操作生产库；既有证据仅在明确未变化范围内复用 |
| UP07 | 本轮日志新路径与旧根目录文件并存 | 旧文件未改动，升级文档能引导定位新旧日志；复用 LG08/LG09 |
| UP08 | 跟随英文指南操作、来源版本超出矩阵、软件降级 | 操作步骤可执行；未验证路径明确说明，不出现删库重建的默认建议；文档与实际标签校对 |
| UP09 | 发布候选与上一 minor／major 路线 | 来源矩阵、具体版本、直接/分步方式及验证证据齐全；不存在上一 major 时说明不适用 |

UP01 使用实际 v0.3.0 发布标签建立旧环境，不能以当前代码模拟注册表代替。v0.4.0 未发布时使用候选提交和独立环境验证，不能提前运行不存在的 v0.4.0 标签命令；发布阶段再核对指南中的标签。旧 v0.2.0 → v0.3.0 的增表证据仅按其历史范围保留，不作为本条新验收路线。测试使用合成数据和明确隔离的库/角色，不需要真实 Token。正式升级路径及备份演练具有写入影响，未来执行时按独立测试环境约束实施，本次只制定条件。

## 7. 与目录整理的关系

本页所链接的历史发布和验收记录，在 BL-017 实施时按 [版本产物目录](development-layout.md) 更新引用；历史版本的证据内容及原始 SHA 不改写。新英文升级指南属于长期运维指南，保留 operations/upgrading.md；每次升级演练的证据归入实际目标软件版本目录，明确来源软件版本，不在 development 根目录继续新增平铺文件。

## revision 2 定稿扩展对升级的影响

上述“四项 working”的无 DDL 契约是首个候选范围；本次新增 [Inspect](inspect.md) 和 [schema 契约](schema-contract.md) 仍保留原六表与 meta 结构，不新增数据库版本列。标准 v0.3.0 库无需迁移；新增严格验证可能识别先前漏检的手工结构漂移，须明确诊断而不修库。Inspect 的 reader 需读取 meta，原仅 raw SELECT 的用户按最小权限说明自行授权；升级不自动 GRANT。原候选证据保留，最终候选重新验证受影响的版本识别、只读权限和旧库操作。schema/inspect 的英文用户文档在实施时交付，不提前宣传未实现命令。
