# 开发工作流设计

本文属于 [当前设计](index.md) 的 v0.4.0，已由维护者确认定稿；不是已经执行完成的流程记录。以已发布软件 v0.3.0 为基线，本轮工作范围以入口列出的四项 working 为准，目标软件为 v0.4.0；发布日期由维护者决定。本文不改写 design-v0.3.0 或软件 v0.3.0 标签。

## 1. 原则与边界

**只有非草案的定稿设计可以实施；测试条件先于实现；软件正式发版由人类明确提出；本地足够完成的工作不触发 GitHub workflow。**

设计与测试条件先进入文档，经维护者确认定稿后，才能开始对应的测试编码和产品实现。草案用于调查、讨论和消除设计矛盾，不能作为实施依据。已有定稿设计覆盖且不受新草案影响的工作可以继续；草案新增或改变的行为必须等待该修订定稿。

“测试先行”首先要求预期独立于实现产生。可自动化的行为，先写测试并确认它因缺少目标行为而失败，再实现；人工体验、真实服务和性能条件也先写检查方法及预期，不要求全部变成单元测试。

本流程不授权跳过既有分支保护、降低质量标准或改写历史。下一版设计是否通过评审、软件是否通过验收、是否发布，分别记录。

## 2. 每个变更的顺序

| 阶段 | 必须先完成的内容 | 可以进入下一步的条件 |
| --- | --- | --- |
| 明确范围 | 用户目标、非目标、受影响行为和兼容性 | 能说明本次解决什么，不将全部 backlog 默认纳入 |
| 设计入文档 | 更新对应规范；涉及数据/CLI/失败路径时明确契约；列出未决问题 | 当前变更内的矛盾和阻塞性问题已解决 |
| 测试条件设计 | 从契约推导输入、预期、边界、不变量及验证方式 | 预期有设计依据，可判定通过或失败 |
| 设计定稿 | 维护者评审自洽设计、测试条件与兼容性，确认非草案版本和范围 | 定稿状态与来源提交可追溯；才可开始对应实施 |
| 测试先行 | 对可自动化行为编写测试，确认预期失败及其原因 | 失败来自尚缺行为，而不是导入、环境或夹具错误 |
| 实现与验证 | 编写满足契约的代码，运行相关测试 | 行为符合设计；发现设计问题则回到设计阶段 |
| 集成检查 | 检查交互影响、用户文档、迁移和受影响回归 | 设计、测试、实现一致，可形成完整变更 |

纯文字修订不必编写无意义的失败测试，可用链接检查、严格构建和人工校对。无行为变化的重构先确认现有回归能保护契约，有缺口先补测试。调查 API 契约可用有明确问题和判定条件的临时探测脚本；探测不替代产品设计，也不直接作为已完成实现合入。

开始实现前，至少记录：目的、行为契约、失败与边界、兼容性影响、测试条件。按变更规模使用几个段落或表格即可，不为每个小改动新建多份模板。涉及需求取舍、破坏性兼容变化或范围扩张时由维护者确认；已授权范围内的常规实现选择无需逐次审批。

## 3. 测试条件如何独立于代码

测试预期来自书面契约、经核实的 API 契约或已记录的用户决定，不能直接复制当前程序输出作为正确答案。

先做等价类划分，再选择边界和故障条件。例如时间新鲜度需要区分未记录、未到期、恰好到期、已到期；日期覆盖需要区分空集合、单日、跨块和范围外。小规模有限状态可穷举，适当使用性质测试验证不变量。有限用例通过不等于证明所有输入正确。

| 条件示例 | 预期与依据 | 验证方式 |
| --- | --- | --- |
| 已有旧接口数据，增加新 API 后初始化 | 原数据、身份及下载记录保留，新增表符合契约 | 独立数据库集成测试 |
| 新增表过程中遇到外部同名对象 | 整次增表回滚，不接管外部对象 | 冲突夹具与 SQL 对照 |
| 下载途中发生块失败 | 已提交块保留，失败和未尝试部分可区分 | 故障注入与报告检查 |
| 窄终端显示运行摘要 | 关键路径和状态可理解，不严重遮挡 | 预先指定场景的真实终端人工检查 |

测试不要求镜像内部函数、临时变量和实现分支；优先观察公开行为和持久数据。时间、网络与故障尽量使用可控夹具；真实 API、性能和人工体验保留独立验证边界。

## 4. 实现反馈与测试修订

发现问题时先分类，再决定改什么；修正当前版本是默认选项，不自动延期至下版。

| 问题 | 处理顺序 |
| --- | --- |
| 实现违反明确设计 | 保持正确的测试预期，修代码 |
| 测试误解设计或夹具错误 | 引用原契约，说明测试为什么错，再修测试；不改变产品语义 |
| 设计遗漏、矛盾或不适用 | 暂停受影响实现，先修订设计、测试条件与决策理由，经维护者确认修订定稿后，再更新测试代码并验证预期失败，最后改实现代码 |
| 新需求明显扩大范围 | 维护者决定纳入当前版本还是延期；延期时明确缺口，不宣称已完成 |

修改测试预期时，在提交说明或对应设计变更记录中留下“原预期、修改原因、新依据、影响范围”。小修正用简短说明；跨章节或行为变化更新草案修订记录。不得仅以“让当前代码通过”为理由删除断言、改期望或刷新快照。遇到 flaky 测试先处理不确定性，不能以跳过代替验收。

先后顺序应可评审，但不强制每一步单独 PR。开发者可以用本地小提交保存设计、失败测试、实现及验证过程；提交说明记录实际失败结果，不伪造测试先行证据。

## 5. 本地检查与 GitHub 的分工

默认在本地完成设计、测试、实现、文档构建和提交。本地足够完成的任务无需 GitHub 介入，不因完成一个功能或一份文档就自动推送、创建 PR 或手动触发 workflow。

仅在必要的开发同步、集成或发布时使用远端，并集中处理关联变更。推送分支、更新 PR、合并 main 和推送标签可能间接触发 workflow，也必须先判断必要性；不能只避免 workflow_dispatch，却以频繁推送触发同样的工作。记录使用远端的具体目的。

本地优先完成 Ruff、相关单元/独立数据库测试、严格文档构建；包安装、真实 API、性能和人工检查按影响范围及验收要求安排。记录实际执行环境与代码提交；有未提交修改时不能把结果错误归属到干净的 HEAD。

GitHub CI 是独立环境复核，并承担分支保护和 Pages 构建部署；本地通过不能替代远端部署成功。保留当前必需检查和保护，集中运行而非取消要求。

证据复用按内容依赖判断：应用代码、依赖或相关配置变化，重跑受影响验证；纯文字补录运行记录可复用未变化的软件测试，文档仍需检查链接和构建。发布候选执行完整自动回归。合并后的树若与候选不同，重新评估差异及影响，不能仅因分支名称相同就复用。

## 6. 定稿、验收和发布

1. 完成设计草案及测试条件，由维护者确认定稿后，才开始对应实施。设计定稿可以在本地完成，不要求先创建 PR、部署文档或发布软件。
2. 根据定稿设计先写测试、验证预期失败，再实现和验证。实现反馈涉及设计变更时暂停受影响部分，先修订设计与测试条件；修订重新定稿后再继续。
3. 对照最终采用的定稿设计完成软件验收，分别记录本地实现验收与远端发布检查。未执行的 CI、部署或人工检查不冒充通过；无需为了推进本地工作提前触发发布检查。
4. 软件正式发版必须由人类明确提出。验收通过、设计定稿或“继续开发”均不构成发版指示；代理不得自行创建或推送正式软件标签、发布 GitHub Release 或启动正式分发。人类明确授权某版本发布后，按其范围完成必要检查与发布操作，不重复索取同一授权。

设计定稿、软件实现验收、软件发布三种状态独立。下一轮设计无需等待前一版发布；若同时存在待发布候选和下一轮草案，分别使用短期分支与明确基线，不混入同一发布提交。

一个尚未发布的软件版本可以采用多次已定稿的设计修订。例如设计 v0.4.0 定稿后实施软件 v0.4.0；发现遗漏时先起草设计修订，受影响实施暂停；修订定稿为设计 v0.4.1 后继续实现软件 v0.4.0。设计版本号按实际变更性质递进，此处仅为示例。最终软件记录采用的设计版本，不要求二者号码相同，也不改写之前的定稿。

设计版本与软件版本继续独立递进。docs/design/ 只维护当前完整设计，历史由 Git 和 design-vX.Y.Z 标签保存；各章共享入口版本。草案号按有意义的完整修订递增，不为每次本地保存递增。软件标签 vX.Y.Z 指向确定的已验证提交，标签不移动。

验收记录写明软件 SHA、设计 SHA、证据和实际状态，可在结果产生后补录。补录文档提交不要求改写已发布标签或无限重复软件验收；文档是否已合并、部署应如实区分。

## 7. 从 backlog 选取工作

Backlog 使用四种状态，与事项分类相互独立。不增加“当前阶段”、进度百分比或重复的设计定稿字段；设计是否可实施以关联设计文档及其定稿记录为准。

| 状态 | 含义 | 正文位置 |
| --- | --- | --- |
| unplanned（待规划） | 已记录，尚未安排 | [待规划](../development/backlog/unplanned.md) |
| planned（已计划） | 已决定做，排队等待开始 | [已计划](../development/backlog/planned.md) |
| working（进行中） | 正在推进，可能是在设计、实施或验证 | [进行中](../development/backlog/working.md) |
| completed（已完成） | 本项验收条件满足，并有完成证据 | [已完成](../development/backlog/completed.md) |

通常按 unplanned → planned → working → completed 流转。明确决定立即开始的事项可以直接进入 working，无需为了走流程短暂经过 planned。进入 working 只表示正在推进，不授予按草案实现的许可；开始编写测试代码和产品实现前，仍按第 2 节核对定稿设计。

每次从已安排的事项中选取少量工作，优先收尾已有 working 再开始下一项，不设固定数量或强制排期。planned 不代表目标版本已经确定；未明确时保留“未定”。排队顺序在 planned 文件内按下一项优先排列即可，不另加优先级体系。

实际操作只需移动一份条目正文、修改状态、同步 [编号索引](../development/backlog/index.md) 的状态和链接；编号不变，引用使用索引固定锚点。移动后核对编号唯一、计数正确、链接有效。正文与索引是同一次编辑，不保留多份副本。状态为空的文件保留入口并注明当前无事项。

暂停推进但仍安排后续完成的事项退回 planned，取消近期安排则退回 unplanned，简短注明原因即可，不增加 blocked 等状态。无需为每天的进展更新状态；短暂等待也不要求移动条目。已完成事项出现新需求时新增关联编号；原验收被证明不成立时允许重新打开原编号，并保留原结论、证据及重开原因。

完成依据取决于条目范围：实现类事项不能仅因设计定稿而完成；纯设计事项可以在其设计交付与评审条件满足后完成；要求实际试行的流程事项必须等试行验证完成。软件是否已发布单独管理，不把未发布自动解释为所有事项都未完成。

当前 BL-014 正在起草和评审工作流，应放入 working；有草案不等于完成。其他事项按维护者安排在状态文件中维护，实时队列以 backlog 索引为准。状态调整不自动确定软件版本范围，不触发远端同步。

### 可操作性与成本

四种状态足以回答“还没安排、准备接着做、正在做、已做完”。设计就绪性由已有文档提供，不在 backlog 复制，因此可以保持轻量。主要维护风险是移动正文后索引失配，用一次本地编号／链接核对和文档构建控制即可；无需新增任务管理工具、自动化服务或 GitHub issue 同步机制。

## 8. 本流程的试行验收

本草案经维护者确认并定稿后，以一个范围清楚的后续功能试行，不默认承诺整个 backlog 都在下一版完成。

- W01：开始实施前能查到维护者已确认的非草案设计及测试条件，关键未决问题已解决；不能按草案新增或改变行为。
- W02：可自动化的新行为有先失败后通过的证据；不适用的变更说明原因和替代验证。
- W03：测试预期发生改变时有独立依据；设计反馈按“修订设计与测试条件 → 修订定稿 → 测试编码 → 实现”处理。
- W04：本地足够完成的工作不推送、不创建 PR、不触发 workflow；必要的远端同步、集成或发布有具体目的，包含对间接触发的判断。
- W05：最终规范、实现和验收证据对应明确；没有因代码不通过而隐式降低标准。
- W06：可以在不发布软件的情况下继续下一轮设计；已有定稿和发布标签保持不变。
- W07：正式软件发版有明确的人类指示及目标版本，不把验收通过或设计定稿当作自动发布授权。
- W08：条目在四种状态间移动后编号不变、正文唯一、索引及计数一致；直接开始、暂停退回和完成判定按第 7 节处理，不增加“当前阶段”字段。

试行后再评估流程是否减少等待和返工。升级指南、Inspect、schema 版本化等业务事项仍分别设计，不由本文替它们作技术决策。

## 9. 本轮四项 working 的关联

本轮按 [backlog](../development/backlog/working.md) 推进 BL-014、BL-010、BL-011、BL-017。工作流设计定稿后，在其他功能的实际实施与验证中完成流程试行；写完本文不代表 BL-014 验收完成。日志目录变更的用户影响进入升级指南；版本产物迁移统一处理四项设计、指南与证据的链接落点。相关定稿设计先于对应测试编码和实现，日志／升级验证产物按已定稿目录规范归档。验收清单集中于 [验收标准](acceptance.md) M 节。
