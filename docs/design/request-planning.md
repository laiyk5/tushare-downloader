# 请求规划算法

版本见 [设计入口](index.md)。本篇包含固定地址块、本地记录选择和交易日过滤完整规则。

## 1. 目标与接口 {#section-1}

优先减少 HTTP 请求次数，接受整块读取带来的重复数据。不是逐行缓存，也不维护任意时间区间集合或持久待办队列。

总体设计负责[命令语义](overview.md#section-3)、[update 行为](overview.md#section-3-2)、[成功判定](overview.md#section-4-2)和[事务](overview.md#section-6-3)。本篇只定义这些需求如何变成请求块。

输入为：命令及显式日期范围、ApiSpec 的查询形态与块定义、接口当前有效日期边界、本地最新日期、已有块检查记录、MAX_AGE/LOOKBACK_DAYS 等已解析配置、固定的本次判断时间。

输出为：有序候选块、实际请求范围、请求或跳过的原因、夹带范围及当前块是否只请求了部分日期。后续请求执行与写入不由规划函数承担；分页细节由 API 适配器处理。

## 2. 固定块计算与边界 {#section-2}

日期接口使用固定时间块，作为请求规划、成功记录和去重的基本单位。目标优先减少 HTTP 请求次数，允许整块读取时夹带已有数据；不做逐行请求去重或任意区间合并系统。

每个 API 明确 block_origin（固定原点日期）和 block_days（正整数自然日数），日期转为相对原点的日序号：

```text
block_id = floor((date - block_origin).days / block_days)
block_start = block_origin + block_id * block_days
block_end = block_start + block_days - 1 day
```

块边界不随用户这次请求起点改变；原点之前的日期也用向下取整，不能用向零截断。时区和日期解释由 API 固定，当前为 Asia/Shanghai。block_days 按接口能力固定，不根据单次返回行数动态改变，不承诺“一个块恰好等于行数上限”。本版五个日频接口均为 1 天一块；未来支持连续日期范围的接口可用更大块，不能假定所有接口都适合周块/月块。

把用户日期区间映射为相交块，按 block_id 去重并顺序请求。每块默认请求完整边界，允许夹带区间外数据并照常入库；前报告同时展示用户范围、实际请求范围和夹带日期。这是固定块的明确约定，不静默假装严格只写用户日期。多个零散需求落在同一块时只发一次块请求，没有需求落入的块直接不选入计划。

接口有效起止范围可以裁剪块边界，不能请求源端支持范围之外的日期；本版五个日频接口显式 fetch/refresh 允许上海当天的暂定数据，update 的默认终点为昨日。当前未结束块记录实际 requested_start/requested_end；成功只表示这次已发布部分已取得，不能据此将未来部分也标为已取得。有效终点扩展后 fetch 必须重新请求整块当前有效范围；refresh 也不能因旧的部分请求仍新鲜就跳过新出现的日期。

块大小/原点属于 ApiSpec 的版本化定义。修改时原始数据保留，旧 spec 的块记录不参与跳过判断，按新编号重新请求并生成记录；不在每次 CLI 中提供改块大小选项。若已有 API 的 spec 变化，按初始化/迁移规则显式处理，不能误用旧记录。

快照没有日期地址，只使用一个固定 snapshot 标识。快照分页或状态枚举、日期块的显式分页可以产生多个 HTTP 请求，但不生成用户任务。源字段、唯一键、规范范围、block_origin/block_days 和更新语义由 API 定义，不增加块缓存服务或额外管理命令。

## 3. 块选择步骤 {#section-3}

1. 按[命令规则](overview.md#section-3)推导本次需求范围和跳过策略。
2. 将时间需求转换为相交块编号，去重并排序；快照使用一个 snapshot 标识。
3. 按块边界计算请求区间，再与接口当前有效日期范围求交；交集为空则不请求，并报告尚不可请求的原因。
4. 检查对应 API/spec/block_id 的记录是否覆盖本次实际区间。旧 spec、缺记录、最近失败或覆盖不足均不能用于跳过。
5. 对记录有效的候选块，按命令决定请求或跳过；输出原因供前报告使用。
6. 对上述本地判断后需要请求的块应用下文交易日过滤；calendar 准备失败停止，不发数据请求。
7. 执行器按顺序请求。只有响应按协议成功处理并提交后，才能更新对应块成功记录；失败规则见总体设计。

命令的需求范围和跳过条件统一引用[总体命令规则表](overview.md#section-3)，本篇不维护第二张语义表。以下伪代码调用该规则，只展开块映射与记录覆盖判断。

以下伪代码只输出本地判断候选；emit_request 的结果还须经过交易日过滤，不能直接发 HTTP：

```text
demand = derive_demand(command, api, local_data, settings)
candidates = sorted_unique_blocks(demand, api.block_definition)

for block in candidates:
    actual_range = intersect(block.range, api.available_range)
    if actual_range is empty:
        report_unavailable(block)
        continue

    record = lookup(api, spec_version, block.id)
    if command == update:
        emit_request(block, actual_range)
    elif not usable_for(record, actual_range):
        emit_request(block, actual_range)
    else:
        emit_decision_using_command_rules(command, record, actual_range)
```

snapshot 路径不执行日期运算；可变型全量取得的网络块不代表可以逐块提前提交或标 stale，仍遵循总体设计的全量事务边界。

## 4. 例子与记录更新 {#section-4}

以 2026-01-01 为示例原点、7 天一块：

| 块编号 | 日期 |
| --- | --- |
| 0 | 01-01 至 01-07 |
| 1 | 01-08 至 01-14 |
| 2 | 01-15 至 01-21 |

用户请求 01-06 至 01-10，得到块 0 和 1，通常实际请求 01-01 至 01-14。假设是 fetch 且块 0 已有有效成功记录，则只请求块 1；假设是 update 的需求窗口，则两块都请求。

如果接口当前只发布到 01-10，块 1 实际请求 01-08 至 01-10，记录该边界。以后发布到 01-11，即使旧记录仍很新，也不能因 01-08 至 01-10 请求成功而跳过新出现的 01-11；重新请求块 1 当前有效范围。

成功写入与块检查记录在总体设计规定的事务内更新。扩大范围后全块重读可能覆盖已有数据，交给业务唯一键处理。失败不延长成功时间，不扩大成功范围。修改 block_days/block_origin 属于块规则变化，旧记录不再匹配；无需搬动原始数据来“对齐块”。

## 5. 测试矩阵 {#section-5}

下列用例验证块计算与总体命令规则的衔接，不另定义命令行为。用例按等价类和边界值选择，特别覆盖跨维度组合。

| 场景 | 预期 |
| --- | --- |
| 起止同一日、位于块首/块末 | 块编号与包含端点规则一致 |
| 跨块范围、多个需求落在同一块 | 去重后的编号有序，每块只计划一次 |
| 日期早于原点 | 向下取整，不能向零截断 |
| 部分块成功、部分块无记录 | fetch 仅跳过符合条件的块 |
| refresh 年龄等于阈值 / max-age=0 | 前者可跳过，后者强制请求 |
| 只增型 update 涵盖新鲜已取得块 | 仍重新请求全部窗口相交块 |
| 当前块成功后有效终点扩展 | 旧成功范围不足，必须重新请求 |
| 需求在有效范围外 | 不请求；报告不可请求部分，不伪造成功 |
| 原点、块大小或 spec 改变 | 旧记录不能用于跳过，数据保留 |
| 快照、可变型全量 update | 无日期游标或新鲜度跳过，遵循各自执行边界 |
| 请求 API 业务码失败 | 不生成块成功事实，按总体重试/失败规则处理 |
| API 成功且返回量达到上限 | 不仅凭行数主动判错；显式分页仍执行 |

这些是待实现测试要求，不表示本文已执行算法测试。测试应注入日期/时间与记录，不调用真实 API。

## 6. 性能与后续调整 {#section-6}

benchmark 比较请求次数、限速等待、夹带行数与总耗时；不以“重复行最少”作为唯一优化目标。块大小由 API 预先配置，先用固定大小建立基线，不实现自适应分块或多层缓存。

需要调整块大小时，在同一变更更新 ApiSpec、对应测试及本设计规则；软件兼容性按总体设计判断。整个设计文档集共享版本，运行时 spec_version 独立管理。

## 交易日过滤 {#trading-day-filter}

### 定位与用户选择权

这是有风险的请求优化，不是数据完整性证明。默认启用，以减少常规休市日请求和空响应警报。
规则和外部在线日历都可能存在例外或错误；正常返回也不保证未来永远准确。
用户通过 `--ignore-calendar` 主动绕过（bypass），或在配置中关闭。此处不再使用“回退”指代该选择权。
程序不得在所选策略不可用时静默降级、关闭过滤或改用另一种判断依据。

保留现有固定单日块算法，不修改 block_id。仅对明确适用的 API 启用：daily_basic、daily、adj_factor、stk_limit、suspend_d 使用中国 A 股常规交易日假设；stock_basic 不适用。
不将所有时间型接口自动视为交易日接口，不要求先证明所有市场日历完整才允许使用基本周末优化。

### 模式

| CALENDAR_FILTER | 行为 |
| --- | --- |
| basic（默认） | 无外部日历依赖；周六、周日过滤，周一至周五请求 |
| calendar | 使用选定交易日历，对候选日期明确判断开闭市；可过滤工作日中的节假日 |
| off | 不进行交易日过滤；命令原有本地记录判断仍生效 |

`--ignore-calendar` 优先于配置，只作用于本次执行；跳过所有周末及日历过滤，也不读取或刷新日历缓存。
不新增交互式降级选择。用户查看诊断后自行重试、改配置为 basic/off，或带绕过选项重新执行。
basic 不声称知道节假日，也不把政府调休工作日当作股市交易日。

周末推断依据：[上交所交易规则](https://www.sse.com.cn/lawandrules/sselawsrules2025/stocks/exchange/c/c_20260424_10816482.shtml)规定周一至周五为交易日；具体节假日另见[休市安排](https://www.sse.com.cn/disclosure/dealinstruc/closed/)。
calendar 模式使用 [Tushare trade_cal](https://tushare.pro/document/2?doc_id=26)。本版五个日频接口以 SSE 日历代表常规 A 股交易日作为优化假设，报告披露来源，不宣称覆盖所有市场例外。
不增加交易所配置矩阵或多个日历提供者框架；未来其他市场/API 需要独立声明适用规则。
有效日历明确为 open 时请求，即使该日是周末；明确 closed 时过滤。该覆盖规则是 calendar 模式的预定规则，不是自动降级。

### 准备、缓存与失败

先按 fetch/refresh/update 原规则筛选本来需要请求的块，再应用过滤。
没有候选块、接口不适用、basic/off 或主动绕过时，均不需要外部日历。
calendar 模式在开始数据请求之前，取得所有候选日期所需的日历；因此准备失败不会产生本次部分数据下载。

缓存按来源、交易所、自然年分文件，保存格式版本、取得时间和逐日日历；不含 Token。
日历请求指定 SSE 和全年范围，不按 is_open 预过滤；与数据请求共用客户端限速、超时和有限重试机制。
重复冲突、非法字段、交易所不匹配等响应视为无效。用于判断的所有候选日期必须有明确记录；缺失日期不得解释成休市，也不得悄悄采用周末规则。
缓存有效期 CALENDAR_MAX_AGE 默认 24h，正时长；age <= max_age 有效。过期、未来时间戳、损坏或不支持的格式不能使用。
缺失/过期缓存允许按所选 calendar 策略刷新；刷新不是降级。每个市场/年份每次执行最多一轮刷新，含有限重试。
成功响应用同目录临时文件原子替换缓存，固定本次使用的日历快照，不在执行中改变判定。

权限不足、请求重试耗尽、无法获得候选日期完整记录或缓存读写故障导致策略无法执行时：退出 1，不启动数据请求；报告 `Calendar preparation failed`、原因及用户可选行动。
非法模式或时长属于配置错误，退出 2。只有主动选择 basic/off 或绕过后，才按相应策略重跑。
日历失败不计成 API 数据块失败；报告单列准备错误、尚未执行过滤判断的候选范围和数据请求数 0，不伪造最终计划。
该约束不保证发现“格式正确但内容错误”的在线日历，用户的强制绕过入口因此始终保留。

`--dry-run` 不请求远端、不写缓存。calendar 模式缓存不足时报告 `Plan incomplete: calendar unavailable` 并退出 1，展示待判定范围和可选行动；不能将其冒充可执行计划。
只用有效缓存时明确日历取得时间；真正执行若缓存刷新，计划可能变化。basic/off 的 dry-run 不依赖日历。

### 命令语义

```bash
# 绕过交易日过滤，仍按 fetch 的有效本地记录判断跳过
tushare-downloader fetch daily_basic -s 2026-09-01 -e 2026-09-13 --ignore-calendar

# 强制重新请求整个范围，包括正常休市日
tushare-downloader refresh daily_basic -s 2026-09-01 -e 2026-09-13 --max-age 0 --ignore-calendar
```

refresh 仅设置 max-age 0 仍遵守过滤模式；update 的回看/完整快照语义不变。
过滤不产生 meta.slices 成功记录，不删除或标记 stale。本地原有数据即使落在过滤日期也不被处理；用户可通过上述强制核对入口检查。

### 报告与计数

成功规划时：T = K + W + H + P。T 为原范围块数，K 为本地记录跳过，W 为 basic 周末过滤，H 为 calendar 日历过滤，P 为计划执行。
类别互斥，先判断 K；calendar 下全部过滤记 H，不再同时记 W。总交易日过滤 G = W + H。
计划记录实际模式、是否主动绕过、规则假设、日历来源/取得时间及过滤范围；报告用 Filtered，不能写 Downloaded 或 Verified complete。
准备失败时 W/H/P 尚未确定，使用 not determined，不套用成功规划恒等式。
calendar_requests 和 data_requests 分别计 HTTP 尝试数（含重试），总耗时包含准备与等待。
全范围已跳过或过滤时可退出 0，报告零数据请求；若访问过日历，不能声称零 HTTP 请求。
数据执行统计与行分类沿用既有规范，ETA 只覆盖 P；日历准备无数据 ETA。

### 验收与 benchmark

- basic 验证工作日、周末、跨年边界，无外部调用；不适用接口不执行过滤。
- calendar 验证工作日休市、周末明确开市、缓存命中/过期/更新以及内容修正。
- 日历缺失、损坏、权限错误、重试耗尽、候选日期缺行：退出非零、无数据请求、无静默降级；诊断说明主动绕过方式。
- 覆盖 dry-run 缓存不足和有效缓存两类；无远端或缓存写副作用。
- 即使提供格式正确但错误的休市日历，用户带 --ignore-calendar 后也能请求对应候选日期；本地记录判断仍生效。
- refresh --max-age 0 --ignore-calendar 请求所有选定日期；过滤记录不会伪装成成功下载或触发 stale。
- benchmark 对照 off、basic、冷缓存 calendar、热缓存 calendar、显式绕过，各五轮；另行测日历失败及时停止，不把它当加速案例。
- 同样本及初始库状态比较请求数、过滤范围、准备成本和总耗时；绕过/off 的数据请求集合一致，不设依赖网络的固定加速倍数。

测试验证既定规则和控制权，不宣称证明外部日历永久准确。
