## 1. 目标与接口 {#section-1}

优先减少 HTTP 请求次数，接受整块读取带来的重复数据。不是逐行缓存，也不维护任意时间区间集合或持久待办队列。

总体设计负责[命令语义](overview.md#section-3)、[update 行为](overview.md#section-3-2)、[成功判定](overview.md#section-4-2)和[事务](overview.md#section-6-3)。本篇只定义这些需求如何变成请求块。

输入为：命令及显式日期范围、ApiSpec 的查询形态与块定义、接口当前有效日期边界、本地最新日期、已有块检查记录、MAX_AGE/LOOKBACK_DAYS 等已解析配置、固定的本次判断时间。

输出为：有序候选块、实际请求范围、请求或跳过的原因、夹带范围及当前块是否只请求了部分日期。后续请求执行与写入不由规划函数承担；分页细节由 API 适配器处理。

## 2. 固定块计算与边界 {#section-2}

日期接口使用固定时间块，作为请求规划、成功记录和去重的基本单位。目标优先减少 HTTP 请求次数，允许整块读取时夹带已有数据；不做逐行请求去重或任意区间合并系统。

每个 API 明确 block_origin（固定原点日期）和 block_days（正整数自然日数），日期转为相对原点的日序号：

```text
block_id = floor((date - block_origin).days / block_days)
block_start = block_origin + block_id * block_days
block_end = block_start + block_days - 1 day
```

块边界不随用户这次请求起点改变；原点之前的日期也用向下取整，不能用向零截断。时区和日期解释由 API 固定，首版为 Asia/Shanghai。block_days 按接口能力固定，不根据单次返回行数动态改变，不承诺“一个块恰好等于行数上限”。daily_basic 首版仍为 1 天一块；其他支持连续日期范围的接口可用更大块，不能假定所有接口都适合周块/月块。

把用户日期区间映射为相交块，按 block_id 去重并顺序请求。每块默认请求完整边界，允许夹带区间外数据并照常入库；前报告同时展示用户范围、实际请求范围和夹带日期。这是固定块的明确约定，不静默假装严格只写用户日期。多个零散需求落在同一块时只发一次块请求，没有需求落入的块直接不选入计划。

接口有效起止范围可以裁剪块边界，不能请求尚未到发布终点或源端支持范围之外的日期。当前未结束块记录实际 requested_start/requested_end；成功只表示这次已发布部分已取得，不能据此将未来部分也标为已取得。有效终点扩展后 fetch 必须重新请求整块当前有效范围；refresh 也不能因旧的部分请求仍新鲜就跳过新出现的日期。

块大小/原点属于 ApiSpec 的版本化定义。修改时原始数据保留，旧 spec 的块记录不参与跳过判断，按新编号重新请求并生成记录；不在每次 CLI 中提供改块大小选项。若已有 API 的 spec 变化，按初始化/迁移规则显式处理，不能误用旧记录。

快照没有日期地址，只使用一个固定 snapshot 标识。快照分页或状态枚举、日期块的显式分页可以产生多个 HTTP 请求，但不生成用户任务。源字段、唯一键、规范范围、block_origin/block_days 和更新语义由 API 定义，不增加块缓存服务或额外管理命令。

## 3. 块选择步骤 {#section-3}

1. 按[命令规则](overview.md#section-3)推导本次需求范围和跳过策略。
2. 将时间需求转换为相交块编号，去重并排序；快照使用一个 snapshot 标识。
3. 按块边界计算请求区间，再与接口当前有效日期范围求交；交集为空则不请求，并报告尚不可请求的原因。
4. 检查对应 API/spec/block_id 的记录是否覆盖本次实际区间。旧 spec、缺记录、最近失败或覆盖不足均不能用于跳过。
5. 对记录有效的候选块，按命令决定请求或跳过；输出原因供前报告使用。
6. 执行器按顺序请求。只有响应按协议成功处理并提交后，才能更新对应块成功记录；失败规则见总体设计。

命令的需求范围和跳过条件统一引用[总体命令规则表](overview.md#section-3)，本篇不维护第二张语义表。以下伪代码调用该规则，只展开块映射与记录覆盖判断。

伪代码只表达规划次序，不新增配置或执行状态：

```text
demand = derive_demand(command, api, local_data, settings)
candidates = sorted_unique_blocks(demand, api.block_definition)

for block in candidates:
    actual_range = intersect(block.range, api.available_range)
    if actual_range is empty:
        report_unavailable(block)
        continue

    record = lookup(api, spec_version, block.id)
    if command == update:
        emit_request(block, actual_range)
    elif not usable_for(record, actual_range):
        emit_request(block, actual_range)
    else:
        emit_decision_using_command_rules(command, record, actual_range)
```

snapshot 路径不执行日期运算；可变型全量取得的网络块不代表可以逐块提前提交或标 stale，仍遵循总体设计的全量事务边界。

## 4. 例子与记录更新 {#section-4}

以 2026-01-01 为示例原点、7 天一块：

| 块编号 | 日期 |
| --- | --- |
| 0 | 01-01 至 01-07 |
| 1 | 01-08 至 01-14 |
| 2 | 01-15 至 01-21 |

用户请求 01-06 至 01-10，得到块 0 和 1，通常实际请求 01-01 至 01-14。假设是 fetch 且块 0 已有有效成功记录，则只请求块 1；假设是 update 的需求窗口，则两块都请求。

如果接口当前只发布到 01-10，块 1 实际请求 01-08 至 01-10，记录该边界。以后发布到 01-11，即使旧记录仍很新，也不能因 01-08 至 01-10 请求成功而跳过新出现的 01-11；重新请求块 1 当前有效范围。

成功写入与块检查记录在总体设计规定的事务内更新。扩大范围后全块重读可能覆盖已有数据，交给业务唯一键处理。失败不延长成功时间，不扩大成功范围。修改 block_days/block_origin 属于块规则变化，旧记录不再匹配；无需搬动原始数据来“对齐块”。

## 5. 测试矩阵 {#section-5}

下列用例验证块计算与总体命令规则的衔接，不另定义命令行为。用例按等价类和边界值选择，特别覆盖跨维度组合。

| 场景 | 预期 |
| --- | --- |
| 起止同一日、位于块首/块末 | 块编号与包含端点规则一致 |
| 跨块范围、多个需求落在同一块 | 去重后的编号有序，每块只计划一次 |
| 日期早于原点 | 向下取整，不能向零截断 |
| 部分块成功、部分块无记录 | fetch 仅跳过符合条件的块 |
| refresh 年龄等于阈值 / max-age=0 | 前者可跳过，后者强制请求 |
| 只增型 update 涵盖新鲜已取得块 | 仍重新请求全部窗口相交块 |
| 当前块成功后有效终点扩展 | 旧成功范围不足，必须重新请求 |
| 需求在有效范围外 | 不请求；报告不可请求部分，不伪造成功 |
| 原点、块大小或 spec 改变 | 旧记录不能用于跳过，数据保留 |
| 快照、可变型全量 update | 无日期游标或新鲜度跳过，遵循各自执行边界 |
| 请求 API 业务码失败 | 不生成块成功事实，按总体重试/失败规则处理 |
| API 成功且返回量达到上限 | 不仅凭行数主动判错；显式分页仍执行 |

这些是待实现测试要求，不表示本文已执行算法测试。测试应注入日期/时间与记录，不调用真实 API。

## 6. 性能与后续调整 {#section-6}

benchmark 比较请求次数、限速等待、夹带行数与总耗时；不以“重复行最少”作为唯一优化目标。块大小由 API 预先配置，先用固定大小建立基线，不实现自适应分块或多层缓存。

需要调整块大小时，在同一变更更新 ApiSpec、对应测试及本设计规则；软件兼容性按总体设计判断。整个设计文档集共享版本，运行时 spec_version 独立管理。
